## 票面重构 + WYSIWYG 打印管道

用户提出两个事：

1. **小票模板是 A4 风的**：现在的 `ReceiptDocument` 走外框 + 横竖线 + 大字距，明显是
   页纸观感，热敏 58mm 上又挤又不像小票。要改成真小票观感。
2. **预览和打印差距很大**：所见所得坏掉了。根因是
   `render.tsx` 里写的 `@page { size: 80mm auto }`，CSS `@page` 的 `size` 不接受
   `auto`，浏览器**直接丢规则**退到打印机默认纸型（A4），于是 58mm 热敏被塞进 A4。
   加上 Dialog portal 会和 `body * { visibility: hidden }` 的兜底 print CSS 打架，
   预览和真打就完全对不上。

### 调研结论

- iframe 隔离打印是 SPA 公认正解（thelinuxcode 的 "Print iframe" + FitToPage.js 的
  动态 `@page` 高度写入）。把 `#print-root` 整段克隆到隐藏 iframe，主文档的
  `<style>` / `<link rel=stylesheet>` 用 `doc.importNode()` 注入 iframe 并把 link
  href 绝对化，再 `iframe.contentWindow!.print()`。
- iframe 不能 `display:none` / `visibility:hidden` —— Chromium 会把它从打印里剥掉。
  用 `position:fixed; left:-20000px`。
- 测高度用 `offsetHeight`（layout 盒模型），不是 `getBoundingClientRect`（后者包
  `transform: scale`，会偏）。
- 等字体 / 布局稳了再打： `doc.fonts?.ready` + `requestAnimationFrame` 双保险。
- `print-color-adjust: exact` 必须显式开，否则浏览器会抹掉边框、底色。

### 落地的两个改动

**A. 票面视觉二分化**（`print/receipt/render.tsx`、`paper.ts`、`types.ts`、`defaults.ts`）：

- 新增 `ReceiptLayout = "receipt" | "sheet"`，`defaultLayout(paper)` 按纸型推：
  卷纸 → `receipt`，页纸 → `sheet`。
- `ReceiptTemplate.layout` 是用户可编辑的覆盖项，`TemplateEditor` 改了纸型会同步
  `patch({ paper, layout: defaultLayout(paper) })`。
- `receipt` 版式：12px SimSun、虚线分隔（`Rule` 单参 `layout`）、左右贴边
  `PaperFrame MAX_FIT=2.5`（58mm 会放大 2.5× 显示，下边框提示
  「按 250% 显示，实际纸宽 58 mm」），没有外框；表头只剩「单号 / 日期」两条 kv，
  **省掉地址 / 电话**（escpos 直打的真票本来就没这两行，58mm 上一行地址就是
  4~6 行纸，省出来 3~4 行救命）。
- `sheet` 版式：保留原 A4 风，实线分隔、表头有完整「地址/电话」，
  `data-page-fixed="1"` 在打印时让 padding 归零。

**B. iframe WYSIWYG 管道**（新建 `print/printPage.ts`）：

- `printJob({ node, paperMm, onAfterprint, onFallbackClose })`：iframe 隔离打印，
  注入样式，绝对化 link，按纸张 mm 写 `@page` 几何，等字体 + raf，再调
  `iframe.contentWindow!.print()`。`onAfterprint` + 120s 安全超时回收 iframe。
- `printFallback()`：主文档直接 `window.print()` 的兜底路径，保留是因为有些
  浏览器对 iframe 打印有兼容问题。
- `ReceiptPrintPreview` 和 `TemplateEditor` 的「打印测试」都换成 `printJob()`，
  **业务页不再写 `window.print()`**。

## 过磅完成后可调整等级（结算时也可改判）

用户提了一个事：化验定级之外，过磅完成到结算这段允许改业务定级，结算时也能改。

### 业务边界（明确写出来）

- **`qc_report.grade`（化验报告上的判定）永不改写**。复检另立新单（不变式 7），
  改判完全不动化验报告。
- **`weigh_order.grade`（磅单业务定级）允许改判**，参与结算/台账汇总。
- 已结算（settled/paid/archived/reversed）的单不能在这里改等级——"等级是钱的
  一部分"，要更正经站长走红冲（02 §F6.3）。
- 已作废（voided）/ 已拒收（rejected）的单不能改。
- 改判必须留事由（≥4 字，与改价事由同责），不写库也不留痕的"没变"情形要短路。

### 设计取舍备忘

- **不动 settlement_order 表 schema**（不加 grade 列）。改判的事后追溯完全靠
  audit_log 的 `settle.create` 备注里的"等级 X → Y"和 `order.grade` 动作的
  `order.grade` 备注两条记录，迁移代价小、查询不受影响。
- **改判时跟着价目表改单价**：等级是定价的第一因，化验定二等结三等的钱常见。
  自动跟价避免"改了等级还挂着旧等级的价"这种最常见的错价。仅对 `matchesList`
  的"价目表带出的价"生效，手填/已偏离议价不动——后者通常是现场口头议价的结果，
  改等级不应该擅自覆盖。
- **改判不重新触发现券收款**。`settle` 路径已经把付款逻辑包了，结算时改判是
  改"用什么价/什么等级结"，不是另开一条流水。
- **`grade` 字段在 SettleInput 用 `Option<String>`，None=沿用**。避免加双层 Option
  区分"未传"与"清为未定级"——结算时清等级没业务意义。
