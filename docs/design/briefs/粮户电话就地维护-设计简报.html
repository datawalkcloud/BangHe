拍板结果：D1 身份框内独立一行；D2 输入框常显 + 显式「保存」（防抖被 uk_party_phone 挡死，不是风格偏好）；D3 摘要态同样给这一行；D4 只把真库那句人话顶到眼前，「打开那张档案」留 Phase-2；D5 车牌防呆与存量脏电话另开一轮；D6 在飞那批已按四条主题提交完，本轮在干净基线上落地。验证：src-tauri 390 passed / 0 failed、ticket-core 17、tsc 与 vite build 退出 0、磅房布局守卫 ALL PASS。

一句话主张：农户电话不是没显示，是被当成住址后面的一段灰字尾巴，磅员在强光下认不出那是电话号码；而身份块正下方唯一带标签、能敲字的格子是「车牌号」。把电话提成有标签的一行、并让磅员当场就能改这一个字段，填错格子这件事就失去了成因。不动存储、不动 DTO 列集、不加迁移、不碰车牌框。

为什么不是"教育用户别填错"：这是界面把可写字段和只读信息摆错了位置的结果，不是操作失误。同一个位置上，一个是灰字、一个是输入框，用户填进输入框是符合界面暗示的正确行为。

3写链路：为什么开一条窄更新命令

3.1 不复用 party_save 的理由（与 party_verify_set 是同一条判断）

复用 party_save({id, phone}) 技术上完全能跑通，但它的审计只有一句 party.update 且 reason = None（orders.rs:1441）。磅房场景里改电话是高频且事后要追责的动作——农户第二天说"我没打过这个电话"，翻审计要能指出哪天哪个磅员把哪个号改成了哪个号。这条信息在 party.update 里根本不存在。仓库里 party_verify_set 的模块头（orders.rs:1510-1511）已经为同一件事写过判据，本轮沿用：

为什么不复用 party_save(id_card_verified=1)：那条命令的审计只有一句 party.update，事后翻审计看不出"这个人是被刷过卡才升的级"，而核验标记的全部价值就在于说得出来源。

5需要拍板的决策

D1推荐 A信息层级

电话这一格放在哪儿？

  • A. 身份框内独立一行，与证号、住址并列（上图）。推荐——它本来就是"这人是谁、怎么联系"的一部分，跟着身份框走才不会被当成单据字段。
  • B. 挪到车牌号旁边做成「车牌 / 电话」两列并排。代价：会被读成"本单的电话"，而它改的是共享档案，语义反而错。
  • C. 保持灰字尾巴，只在末尾加一支笔图标开弹窗。不解决"认不出那是电话"这半个问题。
D2推荐 A技术硬约束驱动

提交时机？

  • A. 输入框常显 + 显式「保存」（或失焦提交）。推荐——uk_party_phone 在，防抖会把 138 这种半截也发出去，撞号红条在输入中途炸出来，磅员不知道哪一位惹的祸。
  • B. 照 OrderMetaEditor 的 700ms 防抖自动保存（:833-838）。车牌/备注能防抖是因为那两列没有唯一约束，电话有。这条不是风格偏好，是被索引挡住的。
  • C. 弹 Dialog 填完再存。多一层手势，且磅房工控机上弹窗会盖住称重读数。

无论选哪个，失败必须原样把真库那句人话顶到眼前（onError: e => toast.error(e.message)），基线 saved.current 只能在 onSuccess 里回填——撞号时不能把没落库的值当已存。

D3推荐 A覆盖场景

制单成功后那一屏（摘要态，今天完全没有电话）要不要也能改？

  • A. 要，摘要态同样给这一行。推荐——「过完磅/结算时才发现电话录错」正是车牌备注已经开口的同一类现场常态（:477-478 注释原话），不给这一格等于把人赶回档案页，而档案页一走就丢了当前单的上下文。
  • B. 只在制单前给。代价：改错要等下一单，或去档案页——正好是本轮要消灭的那条路。

摘要态这一行必须写清「改的是档案，不是本单」，因为同一户的其他单和档案页会同时跟着变。文案：改的是这张档案，历史磅单上印的电话不变。

D4推荐 A撞号出路

号码属于别人时给到哪一步？

  • A. 只把真库那句人话显示出来（「该手机号已是档案「张三」的号码，一人一号，请搜索后编辑原档案」）。推荐做 Phase-1——文案本身已经指了路，磅员点「搜档案」就能走到。
  • B. 再加一个「打开那张档案」的跳转。Phase-2，多一条路由与权限判断。
  • C. 照档案页 DupAdoptHint + adoptParty（PartiesPage.tsx:409-415, 688-693）一键改用那张档案。磅房场景下这等于当场换掉本单的售粮人，档案页能做的事在这里后果重得多，建议不做。
D5推荐 A（但 B 更治本）要不要夹带

车牌框的防呆这一轮做不做？存量 weigh_order.vehicle_no 里已经有 11 位纯数字（PlateField.tsx:77 只收首字符汉字，长度与形状无校验），而且已经印进历史磅单和台账。

  • A. 不夹带，单独一轮。推荐——本轮做完，"以后没必要往车牌里填电话"这个成因就断了；仓库自己的纪律也是这么写的（0028 头注「不动的东西，列在这里免得下一个人顺手做」）。
  • B. 顺手加：车牌整串是 7-11 位纯数字时提示「这像手机号，搬到联系电话？」一键搬。诚实说：B 才治"已经填错"和"手快还在填"，A 只消除动机。但 B 要碰 PlateField 与制单校验，是另一条链路，混进来会让这轮 diff 从"一处 UI + 一条命令"变成三个关注点。

若选 A，我会把 B 连同"存量脏数据要不要洗"一起写进 §7 待办，下一轮单独出简报。

7本轮明确不动的东西

不动为什么
手机号脱敏 / 纳入 pii.read 留痕电话今天在身份卡、档案页、详情页三处本来就是明文铺着，本轮只是把它从灰字尾巴提成有标签的一行，不新增任何明文出口。磅房高频操作逐次留痕会把审计表淹掉。若要收紧，是独立一轮，且要连带处理 PartiesPage.tsx:133/146 那类表单回填。
phone_enc 真上 AES-GCMorders.rs:20-26 自认明文过渡态；一旦随机 IV，密文不可比较，唯一性要迁到 phone_fp 哈希列（0013 头注已写明）。那是加密专项，不夹带。
手机号格式正则校验现在归一 + 查重已够守住"一人一号"。加 ^1[3-9]\d{9}$ 会当场打死存量座机号与带区号的号，属于另一件事。
车牌框防呆与存量脏数据清洗见 D5。下一轮单独出简报，含"历史磅单上印错的电话要不要回洗"这个决定。
PartyPicker 列表行加电话PartyPicker.tsx:101 那行现在显示「车牌 x / 无默认车牌」。加电话是顺手能做的，但会让搜档案那一屏的信息密度跳一档，等这轮界面定了再评估。
PARTY_SELECT 位置 12 那个写死的 NULLdefault_slot_id 在列表里恒为 NULL（orders.rs:1140）是个既有缺口，与电话无关。动它要同时核对三个共享该常量的消费方，别顺手。
