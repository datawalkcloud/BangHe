农产品收购发票 · 进项凭证链 · 设计简报

BangHe 收粮计量结算系统  ·  2026-10-10  ·  状态：待拍板（D1–D8） ·  归属：02 §M12 财务深化 现挂在暂缓表，暂缓理由「需财务口径确认」——本轮要确认的就是那一句

一句话主张：系统开不了票，也不该去开票。收购发票是在主管税务机关核定票种后、由粮站在电子税务局自开的数电票票种；票能不能开、敢不敢开，取决于三件事——卖粮的是不是本人、粮是不是他自产的、粮款有没有付到他本人手上——而这三件事恰好都是这套系统已经在记的。本轮只做一件事：给每一笔收购打上「凭证类型」，把可开收购发票的明细与备查证据链一次导出，并让票面金额和付款流水互相校验得住。算进项、做转出、报税，一律留在财务系统。

为什么不是"在系统里加一个开票按钮"：那需要乐企或税局接口资质（2026 年新出现的银行侧「支付即开票」通道挂在邮储「易企营」，不在我们可控范围内），而真正的风险面根本不在开票动作上——在于我们提供的数据能不能证明这笔收购是真的。

1政策口径：七条已核实的事实（2026-10-10 现行文本）

事实依据对本系统的意义
① 收购发票是"反向开票"：由收购方开给自己作进项凭证。农业生产者销售自产农产品免征增值税、免税项目不得开专用发票，所以票面只注明买价，税额是算出来的，不是票上写的。 《增值税法》免税项目列举
中国税务报 2026-08-05《进一步完善农产品收购发票管理》（"免税项目不能开具专用发票"）		 开票主体是粮站，数据责任也全在粮站。票面每一个字段都来自我们的库。
② 边界收紧：这张票只适用于收购"农业生产者的自产农产品"。同一篇点名三处问题：自产边界易错、买方举证难、错向经纪人开——而"农产品经纪人不是农业生产者"。 中国税务报 2026-08-05 party_type='broker' 必须是硬闸门，不是提示。这条是本轮唯一会导致虚开责任的分流。
③ 扣除率一律 9%，加计 1% 已停。旧口径下购进用于生产/委托加工 13% 税率货物的农产品可在领用环节加计到 10%；2026 年起领用环节不能再加计那 1%。 财政部 税务总局公告 2026年第10号 第五条（二）
（原财税〔2017〕37号、2019年39号那套衔接后停）		 代码与文档里任何 10% / 加计常量都是错的。示例：买价 10,000 元 → 进项 900 元、成本入账 9,100 元。
④ 凭证类型决定"基数"，不决定"税率"。9% 这个扣除率是统一的（③），但乘在什么上面有两种：取得（开具）销售发票或收购发票 → 买价 × 9%；从小规模纳税人取得 3% 专票 → 金额 × 9%；而取得专用发票或海关缴款书 → 按票面注明的税额抵，不乘 9%；从农民专业合作社购进免税农产品 → 9% 扣除率。 财政部 税务总局公告 2026年第10号
12366 答疑（固镇县政府网 2026-07 转发）		 这就是 §2 那张分流表的列定义。系统必须能区分一笔收购拿的是哪种凭证，否则连小计都对不上。
⑤ 免税项目对应的进项不得抵扣；分不清的按占比逐期算，年底再清算一次。 《增值税法实施条例》（国务院令第826号）第二十三条：一般纳税人购进货物（不含固定资产）、服务，用于简易计税方法计税项目、免征增值税项目和不得抵扣非应税交易而无法划分不得抵扣的进项税额的，应当按照销售额或者收入占比逐期计算当期不得抵扣的进项税额，并于次年1月的纳税申报期内进行全年汇总清算。 你们销项免税与应税并存（D0 已确认），所以收购发票的可抵额天生是"先按票面抵、再按占比转出"两段。转出公式需要"不含税销售额 + 无票收入 + 视同销售"作分母——这套数据不在收粮系统里。见 D8。
⑥ 开票有前置资格，不是装软件就能开。收购方需向主管税务机关申请、被归类为"农产品收购企业"并核定该票种；地方执行"先备案后放票，不备案不放票"，备案要核收购场所、设备、业务真实性。 12366 留言答复（农产品收购数电票需到主管税务机关申请）
国家税务总局江苏省税务局 2026-08-13《涟水税务破解夏粮收购开票难题》		 前置动作由会计去办，系统代替不了；但备案要交的材料（场所、设备、真实性）正是本系统能出的一部分。
⑦ 举证与资金流是核查主战场。核查中企业通常被要求提供农民土地承包文件、产能证明；小额散农方向上建议凭村委会自产证明开票。另一侧，2026-09 邮储银行上线乐企联用"支付即开票"：农户在手机银行授权并上传自产证明、企业付款实时到账、支付完成的瞬间联动乐企自动开数电票（货物流/资金流/发票流三流合一）。 中国税务报 2026-08-05
邮储银行乐企联用报道 2026-09-23		 "粮款付到售粮人本人账户"正在从好习惯变成事实门槛。payment_record.method='cash' 的那部分无法自证资金流——见 D6。

诚实边界：上面 ①②③④⑤ 是全国性依据；⑥⑦ 的执行细节各地差异极大（江苏按耕种亩数 500 亩 / 年收购 3000 吨分档引导登记、海南与宁夏各自发正负面清单）。凡标 需主管税务机关确认 的三条见 §5 末尾，不要拿本页当备案依据。

3.1 行源只能是结算快照，不能是磅单

候选行源证据判定

3.2 买价取哪一列（本轮最大的一个数值分歧）

weigh_order / settlement_order 上有三个金额候选：goods_amount_fen（货款）、payable_amount_fen（应付）、paid_amount_fen（已付），另有 deduction_fee_fen、advance_fee_fen 两列扣/垫项（0001_init.sql:219-224）。票面"买价"应等于实际支付给农业生产者的粮款，所以：

本轮倾向：票面买价 = goods_amount_fen；凡是从农户身上扣掉的钱（deduction_fee_fen / advance_fee_fen）一律减掉后才是买价，凡不是粮款的钱（运费、装卸、我方自付的耗材）一律加不进来。

未核实项（必须先读代码再动）：payable_amount_fen 与 goods_amount_fen、两列扣项之间的确切加减关系本轮没有核实——我只确认了四列都存在且语义如注释所述。动手前要先读 orders.rs 里 payable 的算式，把"扣项到底进没进货款"钉死，否则票面买价会系统性偏高或偏低。列入 §5 前置输入 P2。

3.3 三条不变式（可证伪，直接进 §6 守门测试）

#不变式破了会怎样
I1票面每一行的证号、姓名、金额一经生成就冻结——取 settlement_order 快照（§3.1），不随档案改写。补录一个错号，历史票全部对不上原票，且我们说不清哪版是真。
I2票面买价合计 == 同一结算单下 payment_record.amount_fen 合计（:417 CHECK amount_fen > 0）。差额非零的行必须单列"资金流缺口"，不许静默通过；挂账（method='credit_writeoff'）与 payment_status ∈ {unpaid, partial} 天然会产生缺口，那是要报出来、不是藏起来。这是核查时最省事的一条问话："票上写了收 5 万，钱呢？"对不上就是虚开的形状。
I3同一 id_card_no_fp 全生命周期只对应一户。后端写入口必须过 GB11643 校验位；差一位即两档（SHA-256 精确相等，orders.rs:1326-1335）。同一人被拆成多档、单档金额压低——收购发票虚开的标准手法，和"证号录错"在数据上是同一个洞，唯一索引与"已建档"提示同时失效。

I3 的落点很具体：校验位算法今天只在前端（src/lib/format.ts:245-253 validateIdCard，调用点 PartiesPage.tsx:388、QuickPartyDialog.tsx:94），后端 save_party 对证号零格式校验——只 trim().to_uppercase()（orders.rs:1483）后做指纹。party_save 通道能完全绕开前端。见 D7。

5需要拍板的决策

D1推荐 A虚开红线

经纪人拼车代售的粮，票怎么落？现状只有备注预设"司机代售"（0015:63），无结构化清单。

  • A. 建代售农户清单，票开给实际种粮户。推荐——涟水口径明文：小微经纪人走代收代付时"由收购企业直接向种粮户个人开具收购发票"。这也顺带把 02:257-262 那条 P1 未实现的 F3.4 补上，一举两得（它本身也是"代售清单"迎检重点）。代价：磅房要多录一层（谁代售、替哪几户、各多少），是本轮唯一的迁移与唯一的新界面。
  • B. 一律不开收购发票，经纪人的粮进「无进项凭证」桶，只作成本。最省，但若经纪人供货占比高，等于自愿放弃这一大块抵扣，会计那边过不了。
  • C. 照现状开给经纪人。虚开。税务报公开点名"农产品经纪人不是农业生产者"，不做。
D2推荐 AYAGNI / Phase-1

要不要建"开票台账"表，在系统里管开票状态？

  • A. 不建表。Phase-1 只做可开收购发票明细导出（CSV，交会计在电子税务局开），开完把发票号回填 payment_record.voucher_no（死列现成）。推荐——开票动作不在我们这边，建状态机就是凭空造一套和税局永远对不上的假状态。
  • B. 建 purchase_invoice + 明细表，含"草稿/已开/已红冲"。代价：红冲在税局侧发生，我们无法感知，状态必然漂移。留 Phase-2（等接了乐企或税局下载再建）。
D3推荐 A票面正确性

证号、户名、地址要不要进票面？进的话从哪取？

  • A. 进，且详情页单取（不动 PARTY_SELECT）。推荐——收购发票销售方必填姓名 + 证号，数电票还需可核验的身份要素。tax_no 用一条窄查询按 id 取，避开 search_contract.rs:367 与三方共享位置映射的连锁改动。
  • B. 把 tax_no 加进 PARTY_SELECT。不值：要同步改合同测和三个消费方的位置映射，为一个详情页字段动全局列集。
  • C. 票面只留姓名 + 证号、地址留空。看主管税务机关要求，列 P3。
D4推荐 A信息架构

报表落点：并入现有台账还是新开一页？

  • A. 新开一页 /reports/purchase-invoice。推荐——监管台账是固定 20 列列序（02 §F7.1），现导出 29 列；发票明细要的列（买价、扣除率、可抵额、凭证类型、资金流缺口）与它只有前半段重合。混列会同时毁掉两个口径：迎检模板不再可信，发票清单又不完整。
  • B. 在 LedgerReport 加列 + 一个"仅收购发票"筛选。省一页，但筛选一开，列集就和 F7.1 分叉，那份文档要跟着改。
D5推荐 A闸门强度

id_card_verified=0（手工录入、没刷过卡）或证号为空的农户，能不能进收购发票明细？存量里"有电话无证号"的档案是合法存在的（orders.rs:1490-1492 只要求"证号与电话至少一个"，且 :1519 对无证档案强制 verified=0）。

  • A. 能进，但整行标 缺实名核验，并在表头汇总"其中 X 行证号未经读卡核验 / Y 行无有效身份证依据，开票前须补"。推荐——收粮现场先过磅后补证是常态，直接排除会让人改数据去绕过闸门（把别人证号填上），那比缺核验糟得多。
  • B. 硬排除，不进导出。风险：磅房为把粮款结出去而去凑证号，恰好制造 I3 那个洞。且"消失的行"没有任何提示。

复用的是 src/lib/party-verify.ts 已定下的三条闸门判据（已核验空操作 / !card.real 演示卡一律不盖章 / 证号比对由后端重算），不要另写一套"已核实"定义。

D6推荐 A（但 B 更治本）要不要夹带

现金结算的粮款怎么处理？payment_record.method='cash' 在值域里是合法一等公民，现场也确实大量用现金。

  • A. 本轮不改结算闸门，只在导出里单列"资金流"列 + 顶部汇总"现金占比 %、涉及金额"。推荐——把判断交给会计和主管税务机关。注意别说过头：现行全国层面没有"现金支付不得抵扣"的明文（税务报那篇也确认"付款可追溯"属其未提及之列），但银行侧"支付即开票"通道事实要求农户本人账户，现金最脆弱。
  • B. 超阈值现金结算拒绝 / 强制改转账。诚实说 B 才治本，但要碰 settle-gate.ts:66-107 四道闸与 creditPayGate(:124-154)，那是收粮闭环的主链路，混进来会让本轮 diff 从"一个报表 + 两个死列启用"变成改结算。
D7推荐 A补上周的尾巴

后端补齐 GB11643 校验位，本轮做不做？现在校验只在前端（format.ts:245-253），party_save 后端零校验（orders.rs:1483），前端一绕即存脏号。

  • A. 本轮补，范围只到两条写入口（party_save、set_party_verified）：证号非空即必须过校验位。推荐——进项票要的就是证号正确性，这是 I3 的技术前提；且 GB11643 权重全是 11 的非零剩余类，单字符错录与相邻换位必然过不了校验位，可零误报指认档案侧错。
  • B. 另开一轮。代价：中间这段时间导出的票面证号仍可能是错的，而错号发票是我们自己开的。
  • 存量脏号（2026-09-14 提交 35cadc9 之前产生的）只报表、不清洗，与上周结论一致。
D8推荐 A职责边界

免税/应税并存下的进项转出，系统算不算？（D0 你已确认"两种以上并存/还在定"）

  • A. 不算。本系统只按 §2 的 voucher_class 分组出买价小计与按 9% 计算的可抵额小计，明确标注"未扣除免税项目应转出的部分"。推荐——实施条例第二十三条的分母是"不含税销售额 + 无票收入 + 视同销售"，出口免税与即征即退另有归入规则，这些销售额数据压根不在这套系统里（我们只有 outbound_order 出库单）。自己拼一个缺分母的公式，等于造一套看起来能算、实际一定错的账。
  • B. 让会计把当年"免税销售额占比"作为一个数录进来，系统乘一下。能做但危险：那要求逐期算 + 次年 1 月清算两套口径都存，还引出"占比该按季还是按月"的新问题——一旦录入口开了，转出就成了我们该对结果负责的事。

7本轮明确不动的东西

不动为什么
接乐企 / 税局接口自动开票无资质、无接口文档，2026 年这条通道挂在银行侧（邮储"易企营"↔乐企总对总）。这不是工程量问题，是没有我们的位置。
产能 / 亩数 / 单户限额校验系统里没有任何真实来源能给出"这户今年该产多少粮"。硬编一个阈值报警等于造一个假指标，还会被现场当噪音。
销项、应纳税额、进项转出计算见 D8。分母不在这套系统里。
M12 其余项（收购成本、销售毛利、往来对账、费用归集、银行代付回单）本轮只把"凭证类型"这一根轴立起来。02:477 那行 M12 描述要改的是拆出进项凭证链，不是整块开工。
个人所得税代扣农业生产者自产农产品所得的个税口径本页不宣称，与 P3 一并问主管税务机关。
存量重复档案与错号清洗沿用上周结论：只报不清。洗数据要逐户确认，且会倒改历史磅单显示（ORDER_SELECT 是 live join）。
磅单打印模板（receipt/scenarios.tsx）农户手里那张码单要不要印发票号是另一件事——印了也不改变抵扣，却会让现场拿码单当票用。
phone_enc / id_card_no_enc 真上 AES-GCM仍是明文过渡态（orders.rs:20-26、0013:19-21）。一旦随机 IV 密文不可比，唯一性要迁到指纹列——独立专项，别和发票混。
